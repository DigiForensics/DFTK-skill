- **Full QA pass (Round 10) — MCP protocol, all 72 capabilities, and result-contract hardening.** Ran a complete test harness against a live `dftk mcp` session: all 6 tools respond, the two contract traps are confirmed (`dftk_describe` rejects MCP tool names with `unknown DFTK capability`; `dftk_case new` returns the generated `case-…` id used by `show`/`timeline`/`export`). **Executed all 72 capabilities** with best-effort synthetic evidence: **0 server crashes / timeouts**; `describe` is clean for every capability. **Discovered a result-contract reliability gap:** the top-level `ok` flag is `true` even when a capability fails internally (`error`) or receives the wrong input type (`unsupported`) — confirmed 37/72 return `ok:true` without a genuine result (28 `unsupported` + 9 `error`). Strengthened the contract into enforceable behavior: `skills/case-orchestrator/SKILL.md` now inserts a **NON-NEGOTIABLE Step 4.5 "Verify the result"** into the orchestrator loop and a dedicated *Result verification (mandatory)* section with a copy-paste decision procedure (branch on `observation.status`; only `ok`/`complete` is a real result; `unsupported`/`error` → fix-and-rerun as a new `seq`). `references/mcp-setup.md` §8.1 gained the same concrete decision procedure (pseudo-code). `skills/case-orchestrator/references/playbooks.md` and the three worked examples (`worked-engagement.md`, `malware-analysis/examples/worked-triage.md`, `digital-forensics/examples/memory-triage.md`) now each carry an inline verify note. Verified live that the procedure catches masked failures: a wrong-input-type call and a missing-param call both return `ok:true` yet `observation.status` of `unsupported`/`error` (correctly flagged), while a valid `file.hash` returns `ok` with a real sha256. Fixed the relative-link depth of the two new cross-references in the example files (`../../references/` → `../../../references/`).

- **Result-contract fixed at the server (Round 12) — `ok` now honest.** The root cause behind Rounds 10–11 was in the server, not the docs: `dftk mcp` returned top-level `ok: true` for every run regardless of `observation.status`. The fix lives in DFTK 3.3.0 (`src/dftk/mcp_worker.py` + `mcp_server.py`): the worker now derives `ok` from `observation.status` (`ok`/`partial` → `true`; `unsupported`/`error`/`blocked` → `false`), and the gateway distinguishes a genuine worker crash (marked `error_type`) from a semantic failure (which carries a real `Observation`). A regression test was added (`tests/test_mcp_native.py::test_mcp_run_ok_reflects_observation_status`). With `ok` now trustworthy, the workaround-era "never trust top-level `ok`" guidance was replaced across `references/mcp-setup.md` §8.1, `skills/case-orchestrator/SKILL.md` (Step 4.5 + *Result verification*), `skills/case-orchestrator/references/playbooks.md`, and the three worked examples: they now say branch on `ok`, and read `observation.status` only for the granular reason (`unsupported`/`error`/`blocked`). Terminology was also corrected from the non-existent status `complete` to the real `partial`.
